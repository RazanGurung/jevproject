## Current Build

Split Go backend plus vanilla ES-module frontend.

```text
Frontend: web/src/*
  -> REST + scoped trading/market WebSockets
Backend: cmd/server + internal/*
  -> Hyperliquid REST/WS
Exchange: Hyperliquid mainnet + discovered HIP-3 builder perp dexes (xyz compatibility retained)
```

This is a single-user trading app. The browser is the UI and chart runtime; the backend owns signing, exchange transport, bot runtime, market/account relay, and persistence-sensitive flows.

## ⚠️ Rebuild the server after any change

The running server does **not** pick up source edits automatically — it serves a built bundle, so **every change requires a rebuild before it is live**:

- **Frontend edits** (`web/src/*`, `web/index.html`): the server prefers the bundled `web/dist/` shell when present and serves it over raw `/src`. A stale `web/dist/` means none of your changes appear, no matter how the source looks. Rebuild the bundle: `make web-build` (or `cd web && npm run build`).
- **Backend edits** (`cmd/server`, `internal/*`, `pkg/*`): rebuild the binary: `make build`.
- **Do both at once:** `make release` (= `web-build` + `build`), then restart with `./hyperliquid-server` (or `make run`).

`make run` builds the Go binary but serves raw `/src` (dev mode) only if no `web/dist/` exists; if a `dist/` is present it is served, so rebuild or `make clean` it when iterating on the frontend. Rule of thumb: **after merging/adding changes, run `make release` and restart the server**, then confirm the new code is in the served output (e.g. `grep` the feature in `web/dist/*.js` / `web/dist/index.html`).

## Lead Engineer Assessment — July 27, 2026

The current architecture and implementation are approved from a lead-engineering
perspective. The system has clear ownership boundaries: Go owns exchange access,
signing, authoritative trading state, candle history, caching, rate governance,
and recovery; the browser owns interaction, presentation, and render-local
state. Execution safety, bounded concurrency, readiness gating, persistence,
prioritized subscriptions, stale-data handling, and graceful degradation are
implemented as coherent parts of that design rather than as isolated patches.
No architectural redesign or broad cleanup wave is justified by the current
evidence.

The July 27 review reran every Go package and `go vet ./...`, and the frontend
passed **860/860 tests across 131 files**. A read-only check of the operator's
long-running local session found the server ready and healthy after about 23.4
hours, with 1,225 cached prices, the market WebSocket connected, one downstream
market client, and 109 upstream subscriptions against the 900-subscription
ceiling. Active subscription shedding, upstream rate limiting, and downstream
queue drops were all zero. Candle traffic was 38,961 store serves versus 1,329
passthrough serves, or about 96.7% cache-served, and the observed functional API
requests completed successfully.

The noisy-looking lifecycle events in that session are consistent with the
documented design. A browser disconnect demotes its subscription to pending; a
same-client reconnect restores it; and the browser's following subscribe POST
may apply the same intent again idempotently. Hyperliquid and Bybit connection
resets reconnect and restore subscriptions. The cache-owned 64-feed ceiling is
separate from active-client chart priority, while snapshot series counts can
rise through on-demand use and later fall through idle eviction. The cumulative
permanent-feed-drop counter therefore must not be read as current client
subscription shedding.

Deeper investigation should stay focused on measurable boundaries:

- **Startup readiness:** the reviewed 42-market barrier completed successfully
  in 4m29s, but was slower than earlier roughly 3–3.5-minute runs. Track repeated
  cold/restored starts before changing the design; if the drift persists,
  separate snapshot repair, REST budget waits, info-lane queueing, and
  thin-market verification time.
- **Reconnect duration:** distinguish intentional downstream browser rotations
  from true upstream outages. Most reviewed recoveries completed within
  seconds, but a few overnight market-feed gaps lasted several minutes,
  consistent with laptop sleep or network loss. Investigate when a user-visible
  data freeze coincides with those gaps, and measure disconnected duration
  rather than treating every reconnect count as a failure.
- **Subscription capacity:** keep
  `pez_market_upstream_subscriptions`,
  `pez_market_subscription_shed_total`,
  `pez_market_permanent_candle_feed_dropped_total`, and
  `pez_upstream_rate_limited_total` visible together. Current headroom is large;
  do not remove the cap merely to reduce a cumulative drop counter.
- **Execution boundary:** retain the documented modify-order protection re-key
  race as a narrow exchange-semantic limitation, and continue minimal funded
  place/modify-or-cancel validation after meaningful execution changes across
  Standard, Unified, Portfolio Margin, and builder-perp paths.
- **Compatibility boundary:** leave the strategy `window.*` bridge intact until
  concrete strategy work provides enough value to justify browser/runtime and
  funded migration coverage.
- **Maintainability:** improve onboarding and ownership summaries selectively,
  but do not simplify away readiness, persistence, rate governance, or recovery
  safeguards. Prefer observed bugs, risk controls, measured performance work,
  and bounded simplification over speculative restructuring.
