# Architecture

## Purpose

This document defines the current ownership rules. It is not a cleanup plan.

The desired shape is boring data flow:

- the backend owns exchange truth, reconciliation, freshness, recovery, and request priority
- the frontend is mostly a **renderer**: AppState + paint + user intent
- `AppState` owns the frontend render model and ephemeral interaction state
- selectors expose reads
- frontend services are thin adapters over backend APIs (not a second exchange stack)
- streams apply backend frames into AppState and schedule renders
- render modules draw from state
- UI modules adapt DOM events and emit **intent** through market/account session helpers
- `window.*` is compatibility only

Authoritative ownership split (do not invert):

| Concern | Owner |
|---|---|
| Candle history, CVD enrichment at serve time, warm/gap | Backend `candlecache` |
| HL REST weight + info priority | Backend `hlratelimit` + `infogovernor` |
| Order place/protect/sign | Backend `OrderService` + exchange adapter |
| Account/order runtime truth | Backend `AccountRuntime` + trading stream |
| TypeSafe Jev System One / Orderflow Intelligence | Backend `typesafe.Client` + `JevService` |
| Chart paint, ticket DOM, indicator overlays | Frontend |
| Research overlays (e.g. price projection math) | Frontend opt-in diagnostics only — not trading truth |

Release and dependency boundaries are explicit:

- `start (Mac).command` runs `make release`, records the launched PID, validates
  both that PID's repository and executable before stopping it, and refuses to
  terminate an unrelated listener on the selected port.
- npm resolves through the official registry with an exact lockfile;
  `esbuild` is a declared production build dependency rather than an incidental
  transitive dependency.
- `make deps-verify` combines `go mod verify` with a clean staged
  `go mod vendor` regeneration and exact tree comparison against `vendor/`.
- Audit middleware omits high-frequency protected read/control routes from the
  mutating-route log stream. Those routes retain authentication, response, and
  Prometheus accounting; only repetitive audit noise is suppressed.

## Hyperliquid REST Governance

`internal/infrastructure/hlratelimit` is the single process-wide owner of
Hyperliquid REST weight accounting. Its transport wrapper covers every
production request to the official `/info` and `/exchange` endpoints, including
startup metadata, chart history, health probes, account enrichment, bot reads,
signed actions, and each actual retry. Subsystems may impose tighter local
concurrency limits, but they must not create an independent per-IP budget.

- The limiter models the official 1,200-weight rolling-minute allowance as a
  200-weight idle burst plus a continuous 1,000-weight/minute refill.
- `services.OrderPlacementBudget` (historical name `RateLimiter`) is a separate
  **per-address place throttle** at the app edge. It is not HL REST weight and
  must not be treated as a second IP budget.
- Request classification applies the documented ordinary/special `/info`,
  candle-response, and exchange batch weights. Item-sized `/info` types
  (`userFills`, `fundingHistory`, …) reserve their official worst-case extra
  weight **before** the request is sent (2000/20 for fill/order histories,
  500/20 for time-range pages). After the response, the limiter charges only
  the delta so a short page refunds unused reserve.
- Signed `/exchange`, general `/info`, and candle HTTP clients do **not** use
  `http.Client.Timeout`. Limiter wait must not share a wall clock with upstream
  RTT. `hlratelimit.WithRTTTimeout` starts after `Wait` (25s candles, 10s
  probes). The cancel is attached to `resp.Body` (`cancelOnClose`) because
  `RoundTrip` returns at headers; canceling there truncated JSON and served it
  as 200. `/api/chart-candles` parent timeout is 2 minutes so limiter wait is
  not a 504. Truncated-body reads are `passthrough_error`.
- `infogovernor` context lanes preserve execution, visible-chart, account,
  enrichment, and background priority at the shared transport boundary.
  Adapter market reads (`meta`, `metaAndAssetCtxs`, `allMids`, `l2Book`,
  `candleSnapshot`) default to Enrichment, not Execution. `GetAssetCtxs` is
  single-flight per dex and clone-on-serve.
- Price normalization is owned by the exchange adapter (`normalizePerpPrice`):
  exact integer prices remain exact, while fractional perp prices are rounded
  to the stricter of five significant figures and `6 - szDecimals` decimal
  places. Market IOC slippage bounds also call that same function after the
  ±1% mid adjustment (`slippagePrice`) so standard, bulk, close, HIP-3, and
  `isMarket` trigger `p` values share one precision rule. Isolated-margin
  `ntli` is the official signed 6-decimal integer (`usdToNtli`). TP+SL attach
  uses one `positionTpsl` action so sibling cancel is venue-owned.

## Frontend State

Canonical state lives in `web/src/state/store.js`.

Important slices:

- `AppState.trading`: current coin, timeframe, side, order type, price, deployed plan
- `AppState.market`: candles, book, mids, trades, large trades, flow, liquidations, news, stock mispricing
- `AppState.account`: wallet/session, account snapshot, open orders, fills, TWAP state
- `AppState.ui`: chart session, preview state, news-panel visibility (legacy
  `marketRadar*` field names), ticket runtime flags
- `AppState.connection`: active stream/socket, market subscription intent, `marketUpstreamConnected`, and `marketLastTickAt` (real allMids/book/trades/candle only; loopback heartbeats do not count)
- `web/src/state/connection-health.js`: Live/Sync/Offline chrome and `isTradingAllowed()` (local market socket + upstream HL + tick ≤15s). Ticket Place is blocked while not live.
- `AppState.trading.recentCoins`: last five selected coins; book/trade warm-set is active chart + watchlist + those recents, **not** the movers board

Compatibility mirrors live in:

- `state/legacy-globals.js`
- `state/runtime-mirrors.js`
- `bootstrap/window-state.js`
- targeted store mirror writes for legacy readers

Do not add new state owners on `window`.

## Market News Ownership

- Market News is one read-only feed that follows `AppState.trading.currentCoin`.
- It is independent from chart indicators, market subscriptions, account risk,
  ticket sizing, order placement, and strategy execution.
- `internal/services/market_news_aggregator.go` owns direct RSS/Atom polling,
  stable IDs, source health, classification, retention, and stream publication.
- Direct sources share a 20-second scheduler but fail independently. A failed
  source is skipped for 1, 2, 4… minutes up to a 30-minute cap; any successful
  fetch or `304 Not Modified` resets its backoff. One stale/blocked publisher
  therefore cannot become a permanent 20-second request loop or delay healthy
  sources.
- `internal/services/market_data_news.go` owns ticker profiles, the 72-hour
  provider window, sentiment, and deterministic price-impact curation.
- Built-in direct sources cover crypto publishers, Bloomberg Markets, SEC,
  CFTC, Federal Reserve, EIA, and ECB; Google News provides ticker-specific breadth.
- `web/src/services/news-service.js` owns snapshot/stream merging and polling;
  `web/src/ui/signal-radar.js` only renders time, optional BULL/BEAR, and headline.
- The `marketRadar*` and `signalRadar*` identifiers are compatibility names for
  the former scanner UI. They do not imply a scanner or trading dependency.

## Chart Ownership

Adapter invariants, switch/overlay lifecycle, the remaining RVWAP clip, and
the library bump checklist live in [CHART.md](CHART.md). This section is the
module map and ownership rules.

Lightweight Charts 5.2.1 is the only chart renderer. It is a pinned npm
dependency bundled into the production asset graph; production never loads a
runtime vendor script and never silently substitutes a canvas/stub renderer.
The in-memory stub is test-only and requires the explicit
`__PEZ_LIGHTWEIGHT_CHARTS_TEST_STUB__` flag.

- `chart-render.js`: coordinator
- `chart-render-model.js`: runtime snapshots and compatibility-overlay coordinates
- `chart-render-scheduler.js`: render throttling (~16 ms)
- `lightweight-chart.js`: composition layer
- `lightweight-chart-core.js`: chart lifecycle, container, resize, visible range
- `lightweight-chart-series.js`: exchange-native candle series sync (`setData` snapshots, `update` live tail). `update()` is rejected unless the mounted series `coin`/`timeframe` match the incoming tick, so a rAF-deferred recreate cannot append a foreign bar.
- `lightweight-chart-lines.js`: order, position, preview, liquidation, live-price lines
- `lightweight-chart-theme.js`: theme + time-scale/interaction options (`buildThemeOptions`); `layout.attributionLogo` stays off so the chart chrome stays clean
- `chart-interactions.js`: pointer wiring — hover, drag-cursor feedback, vertical price-axis grab-pan, click/double-tap price pick, manual anchored-VWAP placement/editing, and drawing placement/selection/drag + freehand press-drag capture + Delete/Escape keys
- `chart-history-loader.js`: lazy "infinite history" backfill of older candles on scroll-back (LC `barsInLogicalRange` pattern)
- `live-candle-projection.js`: display-only forming OHLC driven by the same mid/L2 price as the native live-price line; it never mutates canonical candles

### Frontend render and request priority

- **Live price path:** mids/book update the native live price line and projected candle every tick (`market-price-runtime`). Topbar digit, document title, and ticket `updateSummary` are throttled (~10 Hz) and skip work when the formatted price text is unchanged.
- **Book path:** L2 does not schedule a full chart overlay pass. Overlay/`drawChart` runs on candle ticks, order/position level changes, and 1m limit auto-track preview moves. DOM ladder remains rAF-coalesced.
- **Liquidations:** stream ingest is immediate; panel DOM is rAF-coalesced (`scheduleLiquidationsRender`).
- **Market News:** rendered from news stream/poll, coin switch, and account render batch only — not from mid/trade/candle ticks.
- **Exchange chrome:** `refreshExchangeInfo` paints meta/mark/OI first; `fundingHistory` applies in a second pass so it cannot delay primary fields under HL weight 20+item cost.
- **Chart REST:** visible series uses foreground `/api/chart-candles` (abortable, fg dedup lane). Adjacent-timeframe, 24h fallback, and VWAP helper work passes `background: true` through the client concurrency gate (max 3 + transient breaker) and uses the backend prefetch lane. RVWAP preparation uses the separate store-only `urgency: 'hydrate'` contract: `200` cache hit or `202` after starting/joining a budgeted warm, never an upstream passthrough. User-triggered selection retains a distinct visible dedup/lane fallback, so it cannot inherit a queued speculative request. Official Hyperliquid `candleSnapshot` weight is 20 + response size; deep secondary series must not race the active chart.
- **Scanners:** primary-tab leadership only for multi-coin pollers so duplicate same-origin tabs do not multiply HL-bound work.
- `manual-anchored-vwap.js`: user-placed pivot-anchored VWAPs, per-anchor deviation bands/σ, per-coin persistence, and marker interaction (startup default off)
- `chart-avwap-editor.js`: on-chart Bands/σ toolbar for the selected origin marker
- `vwap-bands.js`: rolling Kalman VWAP math plus the independently toggleable 7D/30D/90D/365D RVWAP overlay set (30D, 90D, and 365D enabled by default at startup without bands; series title and price-axis badges enabled per preset), driven by a dedicated 4h/600d source rather than display scrollback
- `cvd.js` / `cvd-indicators.js`: CVD math and pane (pane 1) — zero-centered low-intensity histogram bars, outline, and a neutral point at zero on the first available candle of every UTC week. Histogram/outline values include that reset candle's delta; the point makes the reset explicit without delaying or discarding flow. `cvdDelta` from each candle (computed server-side) is the primary delta source; falls back to per-bar directional delta (`close>open ? +vol : close<open ? -vol : 0`) when absent
- `cvd-oscillator.js` / `cvd-oscillator-indicator.js`: bounded [-1,1] price/CVD divergence oscillator histogram (pane 2), reusing the continuous (non-resetting) CVD pipeline
- `monthly-volume-profile.js`: horizontal volume profile supporting Visible Range (default, with PineScript-style contiguous LVN box zones and 3 tiered POC lines), Quarterly, and Monthly periods with 100 price bins (doubled from 50 for enhanced resolution and accuracy), 70% Value Area contrast-scaled bins and clean POC lines (series primitive; VAH/VAL horizontal lines omitted to reduce clutter)
- `whale-markers.js`: on-chart historical whale marker overlay (series primitive) computing large volume bars from completed historical candles at exact `(price, time)` as circles sized logarithmically by notional ($100k to $5M+), highlighting mega whales (≥$1M) with concentric dashed accent rings and bold compact USD badges, zero autoscale distortion
- `price-projection.js` / `price-projection-indicator.js`: research-only
  historical-analogue forecast from confirmed OHLCV. The live overlay is a
  **current-month occupancy map** (series primitive) from the last close
  before that UTC month open through the month’s own bars. Quantile fan
  lines are computed for diagnostics but are not drawn. Disabled at
  startup. Evidence is `unvalidated`. The archived 5/10/20-day freeze does
  not transfer. Data provenance, equations, and non-claims:
  [PRICE_PROJECTION_METHOD.md](PRICE_PROJECTION_METHOD.md).
- `drawing-tools.js`: user drawings (trend line, three-anchor curve, ray, horizontal/vertical line, box, center-radius circle, parallel channel, Fibonacci retracement, measure/ruler, text, freehand pencil, long/short position) as a series primitive, with per-coin persistence
- `drawing-router.js`: fans one toolbar/pointer stream out to the price, anchored-CVD, and CVD-oscillator drawing overlays, translating global Y to pane-local Y and rejecting axes/separators
- `chart-levels.js`: derived chart levels/cache only
- `window.getChartDebugState()`: read-only production diagnostic for live validation. It exposes chart/series lifecycle counts, ownership, visible logical range, `barsInLogicalRange`, pane/overlay attachment, drawing counts, the canonical exchange-candle head/tail, the close-filtered display/RVWAP source signatures, and CVD `resetCount` / `lastResetTime` / `baselineVisible`; it does not mutate chart state.

Chart rules:

- Lightweight Charts owns canvas allocation, pane layout, axes, crosshair, time/price coordinate conversion, logical-range events, autoscale, scrolling, and native price lines. PEZ owns canonical exchange data, snapshot-versus-live lifecycle, series/primitive attachment, interaction policy, and persistence. Do not duplicate library-owned rendering or coordinate state in a second canvas implementation.
- One chart instance owns the container for the page lifetime. Coin/timeframe changes recreate the main series and reattach dependent panes/primitives; responsive resize only calls the library resize path. Authoritative arrays use `series.setData()` and ordered live-tail changes use `series.update()`; rejected/out-of-order **or coin/timeframe-mismatched** updates are diagnostic failures, not something to sort inside the renderer.
- Overlay rebuilds (RVWAP, manual AVWAP, monthly profile, projections, CVD, oscillator) are frame-sliced after the candle `setData` so a coin/timeframe switch can paint candles first. When that switch requested a complete-history overview, the chart **always** re-fits after the last overlay phase — overlay attach can add logical indexes, and treating that shift as a user pan would leave 4h/8h/1d/1M zoomed incorrectly. Projection overlays must not change bar spacing to reveal a long future path — overview fit includes the full fan, while a zoomed-in live edge only extends a small right slack.
- The forming candle is a chart-only projection that follows Lightweight Charts' realtime example: its open stays fixed at the previous completed close, its close equals the native live-price-line price, and high/low retain every observed live-price extreme. The projection uses `series.update()` directly and is keyed/reset by coin and timeframe. It is excluded from `AppState.market.candles`, history/cache, volume, CVD/VWAP/profile math, strategies, snapshots, and API payloads. An authoritative Hyperliquid update replaces/rebases the visible bar; in the narrow boundary race where the next projected bucket exists before the prior exchange final, the native series is rebuilt from the ordered canonical array with `setData()` and the current projection is reapplied.
- Every derived chart renderer consumes a shared completed-candle view, not the canonical array's forming tail: manual AVWAP/bands, Monthly Volume Profile, anchored CVD/reset markers, and the CVD oscillator use the display timeframe's closed rows; RVWAP/bands use closed rows from their dedicated 4h source and project only onto closed display candles. Hyperliquid `T` is authoritative when present; otherwise close time is inferred from the selected fixed, UTC-weekly, or calendar-month interval. This deliberately retains a sparse final row that has genuinely closed. Same-bucket exchange revisions can move the native candle but cannot repaint indicators; the just-completed row enters once when the next bucket opens, and authoritative repairs may still rebuild corrected closed history.
- Price projection follows the same closed-row boundary. The occupancy map
  never appends candles, rebases to the live mid, feeds another indicator or
  strategy, or writes to frontend/backend market state. A new close inside
  the live UTC month keeps the month-open origin and full-month horizon;
  occupancy/weights may refresh. Ordinary forming-candle and price ticks
  must not recompute it. `UpFreq` is a weighted historical terminal
  frequency, `wESS`/`cESS` measure weight concentration rather than
  independent observations, and `BT50`/`BT80` are rolling-origin empirical
  coverage—not formal probabilities or future-coverage guarantees. A gap in
  the retained source makes the model unavailable because all lags and
  targets are defined in bars of the selected cadence.
- Price-scale ownership follows the Lightweight Charts native series model. The
  main candles plus every AVWAP/RVWAP center and band explicitly use the shared
  `right` price scale and leave `autoscaleInfoProvider` unset, so the library
  computes one visible-range autoscale for all price-derived series during
  pan/zoom. Manual AVWAP deduplicates identical candle-revision, anchor, and
  option render signatures so viewport-only changes never replay `setData()`.
  Drawings, Monthly Volume Profile, and the Price Projection occupancy map
  remain primitives attached to an owning series: they convert coordinates
  through that series but intentionally do not contribute autoscale data.
  2-week-path fans attach as native right-scale series but return null from
  `autoscaleInfoProvider` so wide research bands cannot squash candles. Anchored CVD and its oscillator remain native
  series on their own pane/scale domains; they must not be moved onto the price
  scale. This boundary mirrors the official
  [moving-average example](https://tradingview.github.io/lightweight-charts/tutorials/demos/moving-average)
  and [price-scale API](https://tradingview.github.io/lightweight-charts/docs/api/interfaces/IPriceScaleApi).
- If a projected or authoritative update appends a bucket while the complete-history overview is still active, the visible logical range expands on the right and retains its original left edge. This prevents Lightweight Charts' live-edge shift from hiding the oldest loaded candle. Manually zoomed or panned ranges keep the library's ordinary live-update behavior.
- order/position/preview lines come from canonical account/preview state
- TP/SL lines are normal order levels with `tpsl: 'tp' | 'sl'`
- loading-state pair switches must clear native lines immediately
- CVD follows the completed-bar derived-series lifecycle: full historical `setData()` on initial chart load or authoritative snapshot revision, then an O(1) `update()` only when a new closed bucket becomes available. Same-bucket exchange revisions remain canonical/native data but do not change the rendered CVD tail. Histogram `setData`/`update` points are `{ time, value, color? }` or time-only whitespace; helper flags such as `isAnchor` stay internal. The CVD oscillator sends the same time-only whitespace when a short series advances before lag fills, so the lower pane stays aligned with the candle axis.
- CVD's canonical weekly anchor identifier is `1W-MON00`. The legacy `1W-MON14` input remains accepted as an alias, but both reset at Monday 00:00 UTC and diagnostics always report the canonical value. The boundary helper is private to `cvd.js`.
- CVD consumes only exchange candle fields (`cvdDelta`, with directional volume fallback). Mid/mark projection updates never enter canonical candle state or derived-series math
- **CVD delta server-side computation** (`internal/infrastructure/candlecache/store.go` `ComputeCvdDeltas`): the Go server computes CVD deltas at read time, attaching a `cvdDelta` field to each candle in the API response. Enrichment is gated by `chartrequirements.CvdEnabled` at both `ServeInfoRequest` and inside `ComputeCvdDeltas`, so **1m / 1w / 1M never receive composite deltas** even when 5m/30m sources are warm for the coin (1m would otherwise inherit a full 5m directional volume on 5m-aligned opens). The server stitches a composite 5m/30m source stream (5m bars for the recent ~20 days, 30m bars back through Hyperliquid's ~104-day 30m cap; declared 190d) from the existing candle store series, then telescopes directional deltas (`close>open ? +vol : close<open ? -vol : 0`) into each chart bucket. The 5m→30m seam sits on a 30-minute wall-clock boundary, the same instant for every chart timeframe, so the stitch cannot introduce cross-TF divergence. Because every enrichable chart timeframe reads the same composite source, **enriched** (non-nil) CVD values are identical across those timeframes — no client-side source fetching, no session-sticky snapshots, no cache-eviction oscillation; where the server withholds the delta (next bullet) the client's per-timeframe directional fallback legitimately diverges. The 1m chart uses its own bars only (directional fallback); 1w/1M skip CVD. The committed harness `scripts/cvd_validation/` verifies delta correctness and cross-TF identity against mainnet (`docs/LIVE_VALIDATION_RUNBOOK.md` §2b)
- **CVD source health-gating — nil means "fall back", never 0**: a bar's `cvdDelta` is omitted (nil under `omitempty`) whenever the composite can't honestly vouch for the bucket — a source series missing/cold/carrying an unverified gap, the bucket outside composite source coverage (e.g. scroll-back past the reachable 30m window), a bucket **straddling the coverage start** (a partial sum would be silently truncated, differently per timeframe), a **pre-seam bucket finer than 30m** (the 30m-boundary bucket would lump the whole half hour while its siblings fall back — the client would double-count each half hour), a *traded* bucket with zero covering source bars (the stale-source signature: upstream skips empty buckets, so a bucket with volume must have source bars under it), or the **untrusted live tail** of a `degraded` source (closed historical source bars still enrich). When the deep (30m) leg alone is unhealthy, **post-seam buckets still enrich from the 5m leg**; only pre-seam coverage is withheld (previously an unhealthy 30m zeroed the entire series). The client falls back to the per-bar directional delta for exactly those bars. Serving `0` in these cases is a bug (it flatlines CVD instead of falling back); the enrichment loop snapshots only the requested source range under the read lock (`snapshotSourceWindow`), never full-series copies
- **Historical cache residency is separate from live-feed residency**: every on-demand series registration goes through `Store.registerOnDemand`, but the websocket manager admits at most 64 cache-owned permanent candle feeds. Active chart subscriptions are client-owned, sit outside that cache cap, and always take priority. A shed/non-live series can still serve immutable history and a recent tail; once its tail ages, the next read refreshes it through the background REST lane. This prevents a large restored snapshot (hundreds of series) from becoming a same-sized websocket reconnect burst while retaining cache correctness.
- **Chart readiness is dependency-driven and startup-gated**: `internal/chartrequirements` declares every display timeframe's history depth and indicator-source dependencies. The candle store and market-WebSocket ref manager consume that same graph; there is no separate hard-coded list of CVD-enabled intervals. Metadata remains available for every discovered market, while the blocking startup set is intentionally bounded to curated pinned markets plus the highest-liquidity markets passing `PEZ_CANDLE_PRELOAD_OI_MIN` (default $30M notional OI) and `PEZ_CANDLE_PRELOAD_MAX_COINS` (default 60). **Admit barrier (`/readyz`)** verifies only the default landing chart (`2h`) plus shared `5m`/`30m` CVD sources for that universe — history-ready (coverage to `chartrequirements.ReachableLookbackMs`, no unverified gap), not live-tail trust. That helper clamps declared windows to Hyperliquid's 5000-candle retention (30m×5000 ≈ 104d, 5m×5000 ≈ 17d). `NeedsWarm` / `NeedsDisplayWarm`, hydrate, registration, and `ExtendedLookbackMs` use the same clamp, so a restored cap-complete CVD source must not force another universe REST pass after `/readyz`. Remaining `StartupTimeframes` (`1h`, `4h`, `15m`) hydrate in the background after admission via the warm coordinator's `PreferCoins` × `PreferIntervals` pass (the admit-set markets, display-warm, sharing `beginWarm` with every other background fetch); lazy passthrough covers any still-cold switch. **Snapshot restore** loads series `degraded` (live-edge distrust) but serves immutable historical ranges immediately; readiness does **not** re-REST complete restored series just to clear `degraded`. Live-edge memory hits while `degraded` require a `verifiedThroughMs` stamp within two minutes; otherwise the request passthroughs and `scheduleTailRepair` heals the tail. Live edge also heals via the first contiguous WS tick or a present-reaching REST merge. The HTTP listener opens **before** snapshot decode so `/healthz` stays live during multi-second restores; the readiness gate returns `503` for functional/static routes until the admit barrier passes. A hydration failure on the admit set remains fatal. Permanent-feed registration primes the full startup TF set via `PrepareStartupUniverse` before decode so feed priority is deterministic. Snapshots write **columnar v2** (parallel `t/T/o/h/l/c/v/n` arrays; no per-row symbol/interval; no persisted `cvdDelta`); **v1 row format still loads**. Restore uses `restoreCandles` (copy when sorted; merge only if needed).
- **CVD alert scanning is a backend read model**: the browser sends its deduped mover/watchlist coin set once per minute to `POST /api/cvd-scan`. The server reads/heals the 1h candle series through the background chart lane, computes the same continuous CVD oscillator used by the visual overlay, excludes the forming bar, and returns only compact `{coin, barTime, value}` readings. The browser retains notification hysteresis and rendering only; it no longer hydrates one chart history per monitored coin.
- **Live tail enrichment over WS** (`Store.AnnotateWSCandle` / `CvdDeltaForBucket`, wired via `market_ws.go`): enrichable display ticks get the current bucket's composite `cvdDelta` spliced after `ApplyWSCandle` (so a 5m tick contributes to itself; per-bucket sum under RLock, no copies). **`CvdEnabled` is required here too** — 1m/1w/1M ticks pass through raw so a 5m-aligned 1m open cannot inherit five minutes of source volume. The client's `mergeCandle` carries the delta through same-bucket replaces so the completed payload is ready at rollover, while the close-filtered renderer deliberately withholds that forming row.
- Backward compatibility: `cvdDelta` uses `json:"cvdDelta,omitempty"`, so old server builds omit it. The client reads `c.cvdDelta ?? directionalDelta(c)` — absent in passthrough responses and unenriched WS ticks, the overlay uses the per-bar directional delta
- **Frontend cache self-heal for orphaned nil `cvdDelta` bars** (`cachedCvdMissing`, `market-service.js`; hardened July 15, 2026): because CVD is a running cumulative sum, one bar stuck on the directional fallback becomes a permanent level-shift in every later bar until the next anchor reset. The scan covers every actually-completed bar within `CVD_WEEK_LOOKBACK_MS` (8 days); completion is derived from timestamp + interval rather than blindly exempting the final array element, because a thin xyz/native pair may have no current-bucket candle. The 1m chart declares a seven-day weekly-CVD window but first-fetch and cache-enough use `ReachableLookbackMs` (Hyperliquid's 5000 1m bars, ~3.5d). An active chart with missing completed enrichment now refetches automatically on a bounded 30s→5m backoff (eight attempts, canceled on selection change or success), and each live bucket transition re-evaluates the prior tail, so backend source warm-up no longer waits for a coin/timeframe switch to become visible. During a transient source outage, authoritative OHLCV still wins but an already-verified per-timestamp `cvdDelta` is retained until a newly enriched snapshot replaces it, preventing enriched→fallback→enriched oscillation. Bars older than the anchor window are left alone because a weekly reset has already removed their effect
- **Foreground and lid-wake recovery repair content, not only timestamps** (`tab-resume.js` / `market-stream.js` → `recoverActiveCandlesIfStale`; July 15, 2026): a normal focus/visibility return with market-message age above 5s forces an authoritative active-chart snapshot; above 45s it also recycles the market socket. A visible tab may receive no focus event when the whole machine sleeps, so the market heartbeat also compares consecutive ticks against wall-clock time. A tick gap above 30s in a visible tab records `marketWakeDetections`, forces the same authoritative snapshot even inside the current 4h/8h/1d bucket, recycles only the market socket, and reapplies market subscriptions on open. Hidden-tab timer throttling is excluded from wake classification. Chrome `freeze`/`resume`, `online`, and `pageshow` with `persisted` (bfcache) also enter this path; `online` and bfcache always recycle sockets because a zombie `readyState=OPEN` WebSocket is common after sleep. Chart-surface recovery (`recoverChartSurfaceAfterResume`) runs even when stream recovery is throttled: it recreates a lost 2d context, and because official `IChartApi.resize()` no-ops while `autoSize` is on, it briefly disables autoSize, calls `resize(w,h,true)`, then restores autoSize so a GPU-blank canvas repaints. The render scheduler flushes a dropped rAF with a 120ms watchdog. Device-pixel-ratio changes (lid-close monitor detach) also force that repaint. The active-repair single-flight/retry path applies the snapshot, and `candleSnapshotRevision` rebuilds every candle-derived overlay—including CVD reset markers—even when the repaired array has the same count and endpoints.
- **Snapshot revision fans recovery through display-derived series** (`candleSnapshotRevision`, `market-state.js`; July 11, 2026): a REST snapshot, gap repair, or history backfill increments a monotonic revision when it replaces active candles. The chart consumes each revision once with a forced candle `setData()` and full rebuild of anchored CVD, CVD oscillator, manual anchored VWAP, and monthly volume profile. RVWAP is deliberately separate: it rebuilds from its dedicated source revision, so display-history scrollback cannot alter it.
- **Client candle integrity and active repair** (July 14, 2026): every REST/history snapshot is normalized into one strictly ordered, timestamp-deduped, finite OHLCV array before it reaches either the native series or an indicator. Hyperliquid rows are never rewritten or synthesized; malformed rows are withheld and trigger active repair. A detected live jump calls `fetchCandles({forceAuthoritative:true})`, bypassing the otherwise-fresh client cache that already contains the jumped tail. The visible chart retries at roughly 1s/2s/5s/10s (10s capped, jittered for gap repair), one request at a time, and cancels on selection change. Any successful snapshot verifies the interval, including an exchange-authoritative sparse/no-trade interval. Snapshot rows win timestamp conflicts while already-loaded older scrollback is retained.
- The CVD Oscillator (pane 2) renders a bounded [-1,1] price/CVD divergence line off a **continuous** (non-resetting) cumulative CVD (`cvd.js` `'CONTINUOUS'` anchor mode). It computes directly on closed chart bars (no separate source), using the `cvdDelta` / directional delta from each bar. Two normalization details keep the line consistent across all loaded history: (1) all lookback windows are **wall-clock spans** (seconds), *not* bar counts; (2) the price-distance amplitude is a trailing **mean** of `|raw_dist|` (×`AMP_SCALE`, with a `MIN_AMP_PERIODS` floor), *not* a trailing max. Because placement, preview, render, hit-test, and drag all funnel through these two helpers, future support is uniform across tools. (Positions additionally fix their box *width* via `POSITION_WIDTH_BARS`; other tools just track their own anchors.)
- **Multi-pane** (`drawing-router.js`): one router owns overlays for the price pane, anchored-CVD pane, and CVD-oscillator pane. Pane-safe tools (`CVD_TOOLS`: lines, shapes, markers, text, pencil) work in both value-scaled lower panes; fib/measure/positions remain price-only. Pointer events are translated from chart-global Y to the hit pane's local scale, while axes/separators are rejected. A multi-click placement, drag, or freehand stroke locks to the pane where it began. Drawings persist independently under the base, `:cvd`, and `:osc` keys.
- **Placement** is click-based for anchor tools: 1 click (horizontal, vertical, text), 2 clicks (trend/ray/box/fib/measure), 3 clicks (channel), 2 clicks→5 derived levels (positions), **3 clicks for Curve in start → end → midpoint order**, and **click-to-vertex Zigzag** (double-click commits; it is not a press-drag stroke). Curve derives its quadratic control so the rendered line passes through all three editable anchors. Gesture tools use press-drag: Pencil captures a freehand path, while Circle anchors its center on pointer-down and uses the drag distance as its radius; a negligible circle drag is discarded. New circles persist `centerRadius` geometry, while legacy saved corner-based circles remain readable. Previews follow the cursor. **Keep-drawing**: every completed tool stays armed for the next placement until the user toggles it off, presses Escape, or selects another tool (chart scroll/scale remain disabled while armed).
- **Selection/edit**: clicking a drawing selects it (orange + endpoint handles + an on-canvas ✕ delete button clamped to viewport boundaries); endpoints or the whole shape can be dragged (pencil shows no per-point handles — whole-move only). Text drawings can be double-clicked to edit their label and font size. Measure boxes highlight their outline and metrics in selection orange when selected. Selection is exclusive across panes. A capture-phase mouse ownership check claims drawing/anchor presses before the inner chart canvas sees them, so native panning cannot start underneath an overlay drag. While a tool is active or a drag is in progress, the chart's native scroll/scale is disabled and the price-pick/vertical-pan paths in `chart-interactions.js` are suppressed.
- **Delete**: the ✕ button (clamped to remain on-screen even at canvas boundaries), right-click a drawing, `Delete`/`Backspace` on the selection, or topbar **CLEAR** for every drawing in the active coin's price/CVD/oscillator panes. `Escape` cancels an in-progress shape or deselects.
- **Persistence and palette behavior**: drawings are saved per coin to `localStorage['pez:drawings:<coin>']` (price), `localStorage['pez:drawings:<coin>:cvd']`, and `localStorage['pez:drawings:<coin>:osc']`, restored on reload and coin switch. Newly created standard drawings capture the current global Drawing color; existing saved standard drawings keep their recorded color when the palette later changes. Position/directional tools resolve the current Bullish/Bearish colors semantically. Measure boxes render without limit (multiple measure boxes can coexist simultaneously) and persist alongside other drawing tools. Unlike indicator toggles, drawings *are* persisted and remain time-anchored across timeframe changes.

### CVD distance alerts

- `services/cvd-alert-monitor.js` watches the de-duplicated union of top movers and the user's watchlist. The browser sends compact scan requests and owns only per-coin baseline/crossing hysteresis plus alert delivery; it does not hydrate candle histories or calculate the oscillator.
- `POST /api/cvd-scan` owns 1h candle store reads/healing, the fixed 90-day oscillator calculation, and selection of the latest closed bar. Its response contains compact `{coin, barTime, value}` readings, so a forming bar can never trigger a repainting alert.
- Each request is capped at 40 coins. Larger monitored sets are split into ordered, sequential batches of 40 so all movers and watchlist pairs remain covered without an HTTP burst. A scan still running at the next 60-second tick is reused rather than overlapped; after either success or failure the guard releases for the next pass.
- Crossings are edge-triggered at ±0.98 and re-arm only after pulling back inside ±0.50, with per-coin state `{armedHigh, armedLow, lastBarTime}`. The first finite reading establishes a baseline, repeated readings for the same confirmed bar are ignored, and state is pruned when a coin leaves the monitored set.
- Delivery: `onAlert` → `showToast(message, false, {persist:true})` + `playAlertBeep` (`ui/alert-sound.js`, a Web Audio beep, no asset). The alert toast is **persistent** — it stays until the user clicks it (the `persist` option in `ui/toast.js`; renders a `✕` affordance, click anywhere on the toast dismisses it) rather than auto-dismissing after 3s, so an extreme isn't missed while away from the screen. The shared `#toast-container` is **bottom-anchored and capped to the viewport** (`max-height:calc(100vh - 40px); overflow-y:auto`, each toast `flex-shrink:0`), so a run of un-dismissed alerts scrolls internally instead of marching off-screen; new toasts auto-scroll into view. The topbar **CLEAR** composition calls `clearToasts()` and the drawing router's `clearAll()` together. Message carries the side label (`+0.98 (bullish extreme)` / `-0.98 (bearish extreme)`).
- Runs on its own 60s interval **independent of the Market News panel** (`getIsConnected: () => true`); started in `app-runtime.js` `createInit` (alongside `startTopMoversPolling`) and stopped in the before-unload handler. While muted (see *Indicator UI*) the crossing state still advances but `onAlert` is suppressed, so unmuting never replays a stale excursion.

## Market Side Panels (DOM / LIQS)

- The right-side book column (`.book-panel`, 240px) is one unified DOM section. Its **header** renders two backend-owned, exchange-time-ordered rolling samples through the same algorithm: `ALL` retains the latest 500 valid prints, while `WHALE` independently retains the latest 500 prints at or above **$100k**. Ordinary traffic therefore cannot evict a qualifying whale; only the 501st newer qualifying whale can. That latest-500 contract is **top FLOW only** — it does not drive ladder volume-at-price or whale markers. `internal/handlers/websocket/coin_flow.go` maintains both bounded windows and their replay identities, evicts each window's oldest qualifying print exactly, annotates every trades relay with `_flow`, and returns `flowSnapshots` plus accepted/dropped symbols from `POST /api/market-subscribe`. Arrival-order identity FIFO cannot forget a key still in the time-ordered sample, so an out-of-order replay cannot double-count a live print. The first trade-ref **arms** an empty window; after final unsubscribe the cache is deleted and in-flight trades cannot recreate it. `annotateTradesMessage` applies the batch and snapshots `_flow` under the same lock so a concurrent clear cannot publish an empty newer annotation for the prints that just landed. The browser mirrors those snapshots; it does not recompute flow. `state/market-trades.js` keeps the corresponding 500 recent prints for the FLOW header and a per-coin identity FIFO (cap 10,000; the Hyperliquid replay window of 1,200 cannot evict a key) that lives for the subscription (`pruneMarketCoinCaches` drops it) so a resent print cannot double-count session DOM volume. A `0/500` WARM state is explicit before the first public print; once ALL is live, zero qualifying whales is a valid neutral WHALE value rather than a warm-up state. This public-trade flow is independent of chart candle CVD: no CVD calculation, pane, source, or lifecycle changes with DOM zoom or flow updates.
- Pair switches warm the active coin first, then the watchlist and currently visible mover rows through the shared `tradeCoins` intent. Accepted coins keep both `l2Book` and trades hot. On every real selection, `coin-switch.js` first invalidates queued Flow/DOM render frames, then synchronously replaces the active Flow slice. A cache is eligible only when its coin is in the backend's current accepted set, the downstream market socket is connected, and the snapshot's recorded socket epoch equals the current epoch; otherwise the renderer receives `WARM 0/500`, never the previous coin. Subscription responses hydrate their latest flow snapshot and schedule an active Flow repaint immediately instead of waiting for another trade. Incoming books are cached per coin and restored synchronously on selection. If a genuinely cold selected pair still has no streamed book after 250ms, `coin-switch.js` requests `/api/l2-snapshot` with a selection-token guard so a late response cannot overwrite a newer pair. Backend admission remains authoritative under the 900-subscription ceiling; dropped background coins are reported and pruned.
- `render/dom-ladder.js` renders a pooled, fixed-axis ladder whose row count follows panel height. Hyperliquid effective tick size is the base; automatic grouping uses the 1-2-5 sequence with a **×5 trading floor**, fitting only the nearest ten live levels per side and adopting sustained changes after 2.5s. It never widens for old trade extremes. Drag directly on the price spine (up = zoom in, down = zoom out) applies a session-only bias remembered independently per pair; **double-click resets that pair to AUTO**. A normal click still loads the row price into the limit ticket. Bids bucket downward and asks upward, so coarse grouping cannot hide the smaller side near the spread. `state/dom-ladder-state.js` owns **session-persistent** per-tick buy/sell volume, whale markers, and max-print identity for the pair subscription: totals only grow (or clear on pair prune), never shrink because the top FLOW 500 window advanced. Grey flash is time-only (`HIGHLIGHT_TTL_MS` ≈ 1.2s). Unique session price levels are soft-capped (default 2000) by dropping farthest-from-mid entries. Whale markers begin at $100k and use five stages ($100k/$250k/$500k/$1m/$5m). Right-column bar widths use a per-coin high-water max so they do not expand when the max level scrolls off. Book and activity bucketing stay memoized. Live book ticks and trade ticks share one HUD animation frame for `renderDomLadder` / `renderOrderFlow`; `cancelPendingRenders` must not swallow the next schedule after a pair switch.
- `_flow` publishes `buyVol`/`sellVol` with ALL's `sampleCount`, `sampleCapacity`, and oldest/newest exchange timestamps; `whaleBuyVol`/`whaleSellVol` have parallel `whaleSampleCount`, `whaleSampleCapacity`, and whale oldest/newest timestamps. Threshold metadata and numeric `revision` remain shared. The legacy `regularBuyVol`/`regularSellVol` fields describe sub-$100k volume inside the ALL window; because WHALE is now independent, they must not be added to the whale totals to reconstruct ALL. The backend advances one manager-wide monotonic revision when a coin is first subscribed (empty armed window), whenever a new trade batch changes either coin window, and once more when final unsubscribe clears non-empty state; the resulting empty snapshot is a newer revision tombstone, so a cleared/re-created coin cannot reuse or re-qualify older values. The browser orders snapshots by `(market socket epoch, revision)`: a newer epoch can restart at any server revision, while an older same-epoch HTTP snapshot cannot overwrite a newer trades frame. A live trades tick hydrates the HUD only from a just-applied `_flow`; a missing or rejected annotation must not copy an ineligible leftover cache onto the active coin. Releasing the final server trade ref clears both bounded samples and replay identities; a later subscription starts clean.
- `_flow` is the only market-book/trade annotation retained. `annotateTradesMessage` splices it at the message top level as a sibling of `data`, and the dispatcher passes it to `handleTrades`. The upstream read pump decodes a typed envelope (`channel` + raw `data`) so large `l2Book` snapshots are forwarded unchanged without a full `map[string]interface{}` decode. The retired `_signal` and `_wall` values had no remaining consumer after Smart Long/Short and wall-aware pricing were removed.
- **Liquidations are real, not heuristic.** The `liquidation` tag (`{ liquidatedUser, markPx, method }`) lives only on **fills** (`WsFill`), never on the public Hyperliquid `trades` channel — verified live (14.6k public trades / 746 zero-hash system fills carried zero `liquidation` tags) and against the typed `WsTrade`/SDK schemas. The LIQS panel runs the **backend market-wide feed** (Bybit, plus QuickNode when configured); there is no source switcher. `render/trades.js` `getLiquidationRows` reads directly from `AppState.market.marketLiquidations`. **The feed runs on the backend — the browser is a pure renderer** (consistent with flow/classification being server-owned):
  - **`own` liquidations (free):** `handleUserFills` flags fills whose `liquidation.liquidatedUser` is the connected wallet (skipping snapshot replays) and surfaces them as a toast alert plus a `LIQ` badge on the fill row (`normalizeFill` threads `liq`/`liqMethod`). The LIQS side panel itself is market-wide only — own liquidations are not rendered into it.
  - **Bybit (default, market-wide) + QuickNode (optional, HL-native):** each source owns an independently reconnecting goroutine. Before subscribing, Bybit paginates the official linear `instruments-info` endpoint, retains only `Trading` instruments, and intersects them with the canonical Hyperliquid/HIP-3 universe plus the maintained external-symbol aliases. The resulting `allLiquidation.{symbol}` topics are sorted, deduplicated, and sent in deterministic 10-topic batches with unique `req_id` values. Every batch must acknowledge success within the fixed subscription deadline before the feed becomes ready; rejection or an unknown/missing acknowledgement closes the socket, refreshes instrument metadata, and retries. A graceful six-hour reconnect keeps delistings/listings current. Requested/subscribed/rejected topic gauges, a rejection counter, and `/health`/`/readyz` status make transport-connected versus subscription-ready explicit; disconnect publishes zero active subscribed topics. **Side normalization:** Bybit's `S` is the liquidated position side (`Buy` = long liquidated), so `bybitOrderSide` flips it to the forced-order-side convention (`Sell`). When configured, QuickNode HyperCore fills carrying `liquidation` are deduplicated by `tid` and provide the HL-native source. Both feeds publish the same normalized channel and the browser remains a pure renderer.
- This "liquidations feed" is distinct from the chart's grey **liquidation-price lines** (`lightweight-chart-lines.js`), which draw an open position's `liquidationPx` from clearinghouseState.
- Layout is a dedicated 230px grid column (`.liq-panel`, `--col-liq: 230px`) between the book column and the order-entry panel. It is hideable via the **Liqs** toggle button (`#liqToggleBtn`, placed right of the Trade button) which adds `.liq-hidden` to `#mainLayout`. All `.main` responsive states (`radar-hidden`, `trading-hidden`, `liq-hidden`) seamlessly shift column definitions across all 8 permutations, and on mobile view (`book`), hiding Liqs grants 100% width to the DOM ladder. The column stacks three sections: LIQS (`#liquidationsList`) on top, MISPRICE (`#mispricingList`) in the middle, and TypeSafe JEV SIGNAL (`#jevSignalWindow`) on the bottom.

## Market Mispricing (MISPRICE panel)

- **Metric and lifecycle:** the panel ranks supported non-24/7 markets by the distance from the Hyperliquid 1m close at the underlying venue's latest completed close. Backend rows use `(markPx-closePx)/closePx`; open markets are omitted. The browser recomputes from `allMids[coin]` and falls back to the row's `markPx`, so the percentage crosses the threshold and re-sorts live.
- **Exact eligibility:** `market_hours.go` owns a conservative registry keyed by full coin ID, not a DEX-wide heuristic. It spans the audited active non-crypto **`xyz:`** products only (product policy: non-xyz HIP-3/builder dexs are not loaded as markets); the exact registry is also authoritative for `SessionFor`, preventing a second symbol table from disagreeing with scanner behavior. Unknown and crypto products remain absent until their true venue calendar is registered. `make mispricing-audit` compares the checked-in fixture with live `xyz` metadata, while the Go completeness test binds every fixture ID to the runtime registry.
- **Sessions:** session models use IANA zones, weekend rules, ordered regular-market windows, and data tables for maintained closures and early closes. US, KRX, TSE, and HKEX cash calendars are materialized for 2026–2027; SSE is maintained for published 2026 coverage and fails closed beyond it. TSE/HKEX/SSE lunch gaps produce the latest completed morning close. Futures retain explicit venue models: CME/ICE daily and weekend halts, exact KRX day/night windows (including both daily gaps), and continuous Sunday-to-Friday FX hours with no synthetic daily halt. Product-specific futures holiday dates are blacked out rather than approximated with a generic close.
- **Liquidity:** `meetsLiquidityFloor` is shared with market movers. Eligible contexts need notional OI (`markPx × openInterest`) at least `PEZ_MIN_TICKER_OI` (default $3M) and 24h notional volume at least `PEZ_MIN_TICKER_VOL` (default $1M), unless a floor is explicitly set to zero.
- **Backend:** `internal/services/mispricing.go` queries only registry DEXes, canonicalizes names, and applies the registry/metadata/liquidity/session gates before reference availability is considered. Resolved references are keyed by `(coin, sessionCloseMs)`; missing keys are single-flighted, limited to three resolver jobs, and failed keys cool down for five minutes. The selector accepts only the latest valid 1m candle ending at or before the session boundary, never a post-close fallback. Requests serve resolved rows and merely schedule missing work, so candle I/O never blocks the endpoint. Partial DEX/reference failures preserve healthy rows; cached fallback rows are rechecked against the current session so they clear at open.
- **Candle priority:** production injects `candlecache.Store.FetchBackgroundRange`, which shares the background weight budget and one-call HTTP semaphore without registering a permanent 1m feed. The warm coordinator performs candidate discovery independently, finishes interactive chart work, schedules close references, then proceeds to deep 1w/1M history. Active charts are still rechecked between bulk items.
- **Frontend:** `services/mispricing-service.js` starts after 15s and polls every 15s. `render/mispricing.js` applies the absolute ±1% floor, live sorting, mark fallback, close → current tooltip, and requestAnimationFrame batching for midpoint updates. The established `/api/stock-mispricing` path and `AppState.market.stockMispricing` name remain compatibility labels only.

## Trading And Account Ownership

- `services/trading-service.js` owns place/close/TP/SL/high-level execution flows
- `services/order-cancel.js` owns cancel cleanup
- `services/order-modify.js` owns modify flows
- `services/position-close.js` owns optimistic close-position cleanup
- `state/account-state.js` owns selectors and view models
- `state/account-state-orders.js` owns order reconciliation, locks, and recently removed order suppression

Rules:

- frontend order `sz` is USD notional; exchange order `sz` is coin size (modify payloads are coin size end-to-end)
- the normal ticket has one execution path: the user explicitly selects Buy or Sell, then Place Order submits that side. There is no Smart Long/Short auto-direction or smart-price path.
- backend signs and submits exchange actions
- accepted limit/scale orders are locked optimistically by oid when available
- a Hyperliquid modify is cancel+replace: the backend returns the replacement `oid` and both ends re-key immediately (runtime registration + old-oid suppression); never wait for the next snapshot — HIP-3 user-stream coverage lags and the old oid lingers as a ghost chart line
- TP/SL moves go through `/api/modify-order` with trigger fields (one atomic exchange action); the cancel-then-place pattern is forbidden — it loses protection when the place step fails
- cancel suppression is oid-scoped, not coin-wide; bulk-cancel optimism applies only to backend-confirmed `cancelledOids`
- user fills never remove open orders (a fill is not terminal — partial fills still rest); terminal `orderUpdates` statuses remove them
- REST/account-stream repair remains authoritative after optimistic UI cleanup; builder perps have no complete upstream user stream. The backend discovers perp dexes, polls active dexes every 3s, scans inactive dexes incrementally, and reconciles `frontendOpenOrders` every third active tick. `builderPositions` is generic; `xyzPositions` remains as an additive compatibility alias.
- account snapshots expose `accountMode` (`standard`, `dexAbstraction`, `unifiedAccount`, `portfolioMargin`, or `unknown`), `accountModeSource`, and `riskSummaryFresh`. Detection is cached from `webData3` account metadata; it never mutates the user's mode. A legacy `dexAbstractionEnabled=false` alone remains unknown because it cannot distinguish the three current modes. Once a concrete mode is confirmed, a transient/empty `webData3` refresh retains that last-known owner as `cached-stale` instead of replacing Unified/Portfolio collateral with the meaningless individual-perp zero. On a failed account fan-out, the bounded last-known account snapshot is returned explicitly stale rather than HTTP 500; frontend continuity preserves its last fresh collateral fields only while `riskSummaryFresh=false`. A fresh owner-reported zero remains authoritative.
- builder identity is process-wide: Go `pkg/utils.IsBuilderPerpCoin` / `GetDexName` is the routing classifier; `IsHip3Coin` is xyz **category** only. Adapter `resolveMarketVenue` and runtime `isRuntimeBuilderPerpCoin` delegate to that helper. Frontend mirrors with `isBuilderPerpCoin` / `getDex` / `isHip3Coin` — no new `startsWith('xyz:')` routing checks.
- builder account state is only via `GetBuilderDexState` / `GetBuilderDexes` on the exchange port (no `GetXyz*` dual methods). Downstream user-stream channel name `xyzPositions` remains a wire compatibility label for the xyz poll path.
- WebSocket manager is three embedded runtimes (`DownstreamHub`, `MarketFeedRuntime`, `AccountFeedRuntime` in `runtime_feeds.go`) plus narrow `FillProcessor` / `BotEventHandler` hooks; market fanout is `BroadcastMarket`, trading fallback `BroadcastTrading` (legacy names alias).
- Drawing: `drawing-model.js` (types/persist), `drawing-render.js` (shape paint + handles), `drawing-geometry.js` (hit math), `drawing-tools.js` (coords + pointer lifecycle binder). Research projection under `web/src/research/`. Chart candles: `chart-candle-service.js`; RVWAP: `rvwap-source-service.js`; `market-service.js` is poller/reference façade.
- queued TP/SL protection persists to `pending_protection.json` (no private keys); entries survive partial fills (each fill attaches its own legs, deduped by trade id so reconnect snapshot replays are idempotent) and retire on terminal `orderUpdates` — cancel-like immediately *unless* an earlier partial fill left a leg incomplete (kept, closed to new fills, for the retry sweep), `filled` after a grace window for racing/replayed fills
- TP and SL are tracked and retried as independent legs (`protectionAttachUnit` in `order_service.go`): one leg failing never suppresses the other, a failed leg is retried by a background sweep (~20s) forever rather than being silently dropped, and a leg that already succeeded is never re-placed — see `docs/API.md` "TP/SL protection attach retry"
- a synchronous fill is persisted under `immediate:<oid>` before protection placement. When the same terminal fill later arrives on `userFills` with a trade-id key, it is routed to that existing unit rather than creating a second TP/SL pair.
- order/fill event bursts request one coalesced authoritative account refresh. That path refreshes the portfolio summary, normalizes the snapshot through the same code as REST, stamps `accountSnapshotAt`, then broadcasts fresh account/risk fields on the scoped `webData2` browser channel so top-right Portfolio Value and Available update even when upstream `webData2` omits `clearinghouseState`; accepted frontend actions also schedule a forced REST read that bypasses the short burst cache. `Available` means unleveraged free collateral from the clearinghouse that owns it: perp `withdrawable` for Standard/DEX-abstraction accounts, and the lesser of spot `tokenToAvailableAfterMaintenance` and spendable spot USDC (`total - hold`) for Unified/Portfolio-Margin accounts (whose individual perp-dex states are not meaningful per Hyperliquid's account-mode contract). The minimum matters while resting orders reserve spot holds. An owner-reported zero is authoritative. Older timestamped snapshots cannot overwrite newer account metrics; explicitly stale/partial snapshots retain a stale marker rather than pretending to be fresh.
- builder-dex post-trade repair has its own per-`account|dex` single-flight. `orderUpdates` and `userFills` for the same execution commonly arrive together; a 75ms debounce collapses that burst into one targeted builder-state fetch instead of consuming two `/info` requests. If another event arrives while the fetch is running, it marks the key dirty and schedules exactly one follow-up pass after the current fetch completes. Different accounts or dexes remain independent, each fetch retains its 3s deadline, and the normal builder poll/cache remains the eventual-consistency fallback. This repair path never blocks signing, the trading-stream write queue, chart reads, or market-WebSocket dispatch.
- bulk modify/cancel reconciliation is per-status, not batch-optimistic. Partial responses retain aligned replacement-oid slots (`0` means unconfirmed); backend runtime state and frontend chart state update only confirmed entries. Mixed stale/valid bulk cancels return confirmed `cancelledOids` with `status:"partial"` instead of hiding successful cancels behind HTTP 500.
- post-fill TP/SL requests carry the exact filled coin quantity internally. They never reconstruct quantity from notional at the TP/SL trigger price, which can floor the stop leg by one size increment and leave a position under-protected.
- position-panel TP/SL requests also send authoritative `szCoin` alongside legacy USD notional, and optimistic locks store coin units. Trigger-price rounding can otherwise turn `size × unroundedTrigger` back into one fewer size increment. Plain opening-order modifies are preflighted against Hyperliquid's $10 minimum on both frontend and backend: a cancel+replace drag below the minimum is rejected locally because the venue may cancel the old order before rejecting its replacement.
- aggregate account and open-order reads are bounded hot paths (8s overall, 3s per builder dex; forced decorative portfolio refresh gets 2s). Builder failures remain partial/stale rather than allowing one venue to consume the former 30s request budget.
- position close buttons send the row's signed `positionSzi` as well as absolute `positionSize`. Standard and builder close paths derive direction from that authoritative rendered value and skip the redundant clearinghouse lookup; legacy API callers without `positionSzi` retain the lookup fallback. This matters for 25/50/75% closes: live validation found the old lookup could stall the button beyond 12s even while direct account reads remained healthy. Fractional sizes are floored to the coin's `szDecimals` before signing (`0.00017 BTC × 25%` becomes valid `0.00004`, never invalid `0.0000425`); a partial whose resulting notional is below the venue's $10 reduce-only minimum is surfaced as an exchange restriction, so the user must use full Close.
- execution precision is metadata-authoritative. Standard and builder perp prices use the same Hyperliquid rule (five significant figures and at most `6-szDecimals` decimal places), and size formatting uses the exchange-provided `szDecimals`. A cold metadata failure aborts before signing; no default precision is guessed or cached. Successfully verified execution metadata refreshes after 30 minutes but remains available as an explicitly stale outage fallback for up to 24 hours. Bulk market orders use the same direction-aware 1% IOC slippage bound as single market orders.
- reduce-only intent is orthogonal to time-in-force. Every single/bulk and
  standard/builder market path preserves the caller's `reduceOnly` value in the
  signed wire action; selecting IOC controls whether a remainder may rest, not
  whether the order can increase exposure.
- the market WebSocket primes one short-lived execution-mid cache with every standard and builder `allMids` update. Market orders and position closes read that cache before bounded REST fallback. This removes a redundant `/info` dependency from the close hot path; funded validation reproduced the old `could not get mid price for BTC` failure during account-fan-out contention and confirmed cached BTC/GOLD closes at roughly 0.7–0.95s after the fix.
- only actual trading controls are exported to the browser compatibility surface. The former `bulkModifyOrdersUI`, `cancelByCloidUI`, and `updateIsolatedMarginUI` prompt helpers had no rendered button, delegated action, or production caller and were removed; their backend APIs remain available to external clients.
- the stream-health watchdog force-reconnects the upstream user websocket when account state goes silent (bounded at 2 consecutive attempts, then warn-only on REST fallbacks); it runs even with zero browser clients connected because pending TP/SL protection rides the userFills stream
- the xyz poller doubles as a sleep/wake detector and, after a >30s tick gap, cycles **all** upstreams (`closeAllUpstreamsForWake`: market, user, and tracked liquidation sockets) and `Reset()`s reconnect backoff. The gap MUST be measured in wall-clock millis (`wakeGapExceeded`), never `time.Since` — Go's monotonic clock (CLOCK_UPTIME_RAW on darwin) pauses during system sleep, so a monotonic comparison can never observe a sleep gap (the first real lid-close session proved this: five wakes, zero detections, every recovery rode the wall-clock watchdog by accident)
- a market order's unfilled IoC remainder is cancelled (slippage cap on a thin book), so the frontend flags fills below 97% of the requested notional with a partial-fill toast (includes residual USD and fill %); limit remainders rest on the book and are not flagged
- place/bulk responses echo the wire `cloid` (auto-generated when the request omits one) so clients can cancel-by-cloid or reconcile without guessing
- position closes are IOC reduce-only; `/api/close-position` reports `requestedSzCoin` / `filledSzCoin` / `residualSzCoin` / `partial` when the fill is below 97% of the requested coin size so an IoC shortfall is not a silent full-ok
- modify re-key protection: after a successful exchange modify, protection is re-keyed to the replacement oid **immediately** (account pre-resolved; re-key runs before runtime registration). An old→new **alias** keeps fills still keyed by the pre-modify oid attached to the same request; order-update cancels do **not** follow the alias, so the exchange cancel of the old oid cannot clear replacement protection. Residual race is only the theoretical gap between exchange return and the re-key lock (no address derivation in that window)

## Stream Ownership

- `/api/trading-stream` and `/api/market-stream` are the only downstream realtime connections; each owns its queue, sequence, and reconnect lifecycle
- Hyperliquid `/info` and `/exchange` share one process-wide official-weight
  budget at the HTTP transport boundary. `internal/infrastructure/infogovernor`
  supplies lane priority and tighter concurrency in this order: execution,
  visible charts, core account repair, optional enrichment, and background
  warming. WebSocket dispatch never waits on either REST control.
- visible and speculative chart reads enter through `/api/chart-candles`; visible reads use the protected four-wide passthrough lane, while prefetch uses a separate one-wide lane. CandleSnapshot upstream calls share the HL weight transport with `Timeout: 0` and a 25s RTT bound that starts after limiter wait; short probes use a 10s RTT bound on the general client. The handler budget is 2 minutes.
- synchronous account repair fetches main/spot/xyz core state only. Other builder DEX state comes from the dedicated poll/cache, and an order/fill targets only its affected DEX for immediate asynchronous repair
- `POST /api/market-subscribe` updates client-scoped market intent, including the optional validated `indicatorIntervals:["4h"]` RVWAP source. Its response reports `acceptedTradeCoins`, `droppedTradeCoins`, and revisioned `flowSnapshots`: all accepted coins exactly once for a fresh market-socket epoch, then only newly added membership. An identical set or rank-only reorder is a backend no-op and does not churn references, logs, Flow windows, or snapshots. Frontend requests carry monotonically increasing generation tokens and abort in-flight POSTs when generation moves; only the newest generation in the current market-socket epoch may update acceptance, caches, render state, or subscription dedupe state. This makes overlapping A→B→A responses harmless. New indicator candle refs are counted in the same 900-slot admit math as book/trade pairs, so enabling RVWAP at the ceiling sheds a newly requested background pair instead of oversubscribing. Book/trade symbols requested for DOM/Flow are the active chart, watchlist, and up to five recent coins — movers rank changes must not add L2/trade subscriptions. Apply logs report `added`/`dropped` counts. On upstream reconnect, phase 1 re-subscribes each visible client’s `chartCandleRefSet` plus book/trades before keepalive; phase 2 remainder failure is fatal for that connect. Last client candle-ref `0` notifies `OnCandleFeedDropped` so a shed series cannot serve a stale live tail.
- upstream subscriptions are capped at 900 (below Hyperliquid's documented 1,000-per-IP ceiling): accounting includes the default `allMids` feed plus every discovered builder-dex `allMids` feed. The active chart is never shed; dormant permanent candle feeds yield first, then background watchlist/tracked book+trade pairs may be omitted. This is observable through subscription responses and `pez_market_*subscription*` metrics.
- market stream modules route transport frames and update canonical market state
- account stream modules apply revisioned backend snapshots/deltas and render hints; backend code owns enrichment and reconciliation
- reconnect and tab-resume behavior should be measured with `window.transportMetrics`
- upstream market, user, and liquidation reconnects use interruptible exponential pacing from 1s to 30s and reset after a session stays connected for 30s. Waits are wall-clock (`waitThenMaybeReset`: 250ms ticker on `UnixMilli`); if the host slept through the delay (`wakeGapExceeded`), backoff `Reset()`s to the minimum instead of leaving Darwin monotonic leftover. Upstream metrics expose market reconnect phase plus source-scoped liquidation reconnects and completed-session duration; downstream market metrics separately expose attempts, connects, scheduled reconnects, refresh reason, and heartbeat timeouts. Server logs include downstream close codes/reasons, making browser-initiated refreshes distinguishable from transport failures.
- backend fanout to browser stream clients must stay non-blocking relative to upstream Hyperliquid reads
- each downstream lane owns a bounded write queue (`marketSendQueueSize = 2048` for high-throughput market feeds, `tradingSendQueueSize = 512` for account/order execution); a stalled market client cannot fill or close the trading queue
- on client connect the server immediately pushes an `allMids` snapshot from the BBO cache (entries fresher than 60s **and** `IsMarketConnected()`) and an `initialState` account snapshot, so a (re)connecting tab paints without waiting for the next upstream tick. BBO timestamps are `UnixMilli`, never monotonic `time.Since`. If the upstream Hyperliquid market socket is down, the snapshot is empty — a connected local `/api/market-stream` plus loopback heartbeats must not paint sleep-stale mids as live. Connect-time BBO frames set `snapshot:true` and do not stamp `marketLastTickAt`. Downstream also receives `{type:"upstream", connected}` on upstream connect/disconnect; `{type:"heartbeat"}` broadcasts every 15s (matching the trading stream ping interval and providing a 4× safety margin against the 60s client watchdog) — it is not market data and only refreshes Live/Sync/Offline chrome. Only `allMids` / `l2Book` / `trades` / `candle` count as live ticks.
- tab resume is silent by default: the recovery overlay is armed only when the account socket is genuinely closed or stale (>45s without a message). Market data uses two independent thresholds driven by `lastMarketPayloadAt` (real `allMids` / book / trades / candle — not loopback heartbeats): >5s without a market payload forces one authoritative active-candle snapshot, while >45s also recycles the market socket; a healthy resume only performs the ordinary timestamp-freshness probe. Market heartbeat starts at connect, including CONNECTING.
- the first downstream reconnect attempt is immediate (backoff starts at the second attempt); resume paths reset the backoff and short-circuit any pending retry timer
- every fresh market socket advances the Flow cache epoch, retains but invalidates old per-coin cache freshness, clears the active Flow slice to WARM, and re-sends market-subscribe intent; trading reconnects never touch market intent
- A ref-count update captures one upstream subscription writer. After its first
  socket write failure, the writer suppresses later writes in that same update
  while all local ref mutations continue; the degraded socket is cleared and
  the next connection replays the final ref state. This avoids one broken-pipe
  log per remaining unsubscribe without weakening recovery.
- the backend demotes a disconnected client's market subscription state to a pending entry (10-minute TTL) instead of deleting it, and restores it when the same clientId reconnects only after a short grace (`pendingRestoreGrace`, 500ms) if no re-subscribe POST arrived — defense-in-depth for a lost POST without an intermediate thrash on healthy lid-wake reconnects; a fresh subscribe POST always wins, and a late pending apply is a no-op once live intent exists
- browser trading and market heartbeat/wake detection are independent. A trading-stream wake recycles the account socket; a market wake increments `window.transportMetrics.stream.marketWakeDetections`, repairs the candle tail authoritatively, cycles only the market socket, and reapplies market subscriptions. Live-price-line age uses `marketLastTickAt`; tab resume must not `touch()` that timestamp. Backend process wake (xyz poller / user-WS gap) still closes every upstream, including liquidation.
- converging recovery triggers (wake tick, visibilitychange, heartbeat staleness) are debounced by a 2s refresh-suppression window after a fresh connect
- candle freshness is probed directly on tab resume and stream (re)open (`recoverActiveCandlesIfStale`). A proven browser suspension forces the authoritative path even when the last timestamp is in the current bucket; otherwise the ordinary probe uses display-timeframe age. The `fetchCandles` cache hit requires both sufficient span AND a fresh tail (last candle within max(2.5×interval, 90s)) — span alone masks a stale tail

Transport modules must not own trading rules.

Signed exchange transport is bounded-concurrent rather than globally serialized. `PEZ_EXCHANGE_MAX_INFLIGHT` defaults to 8; monotonic nonce allocation remains independently locked. Queue time, request time/result, and current in-flight work are exported as `pez_signed_action_*` metrics. Signed mutations are never automatically replayed after an HTTP/transport error — including `http 429` and `5xx` — because the exchange may already have committed them. Those failures return `ambiguous:true` on `CanonicalOrderResult`; the browser must not mint a new cloid and retry. Orders carry a 128-bit hex `cloid`; ordinary calls generate it cryptographically and persisted TP/SL legs derive and reuse a stable id. Place/Bulk reject below Hyperliquid's $10 min open notional instead of silently sizing up. Cancel paths nack missing per-oid statuses rather than treating an incomplete venue payload as full success. Trigger modify sends `LimitPx` from `triggerExecPrice` and the trigger wire type from the trigger itself; `PlaceTriggerOrders` fails the whole request if the venue returns no statuses. Scale preview rejects an unknown tick. Flatten / cancel-all require an explicit confirm. Server-owned background work derives from the process lifecycle context so graceful shutdown cancels bots, protection retries/attachments, account refreshes, mispricing resolves, cache work, and feed goroutines.

## Backend Ownership

Backend layers:

- `cmd/server`: process setup and route registration. The `http.Server` sets `ReadHeaderTimeout` 10s and `IdleTimeout` 120s. Gin `SetTrustedProxies(nil)` so `X-Forwarded-*` cannot spoof client IP. HSTS is emitted only when `c.Request.TLS != nil`. CORS `Allow-Methods` includes PUT (color-palette templates). When `PEZ_API_TOKEN` is set, identity/status reads (`GET /api/bot/status`, `GET /api/has-saved-key`, `POST /api/key-address`, `GET /metrics`) are token-gated with the fund-moving routes.
- `internal/handlers`: HTTP/WebSocket adapters
- `internal/services`: domain workflows
- `internal/infrastructure/exchange`: Hyperliquid adapter
- `internal/domain/models`: request/response models

Backend rules:

- the Hyperliquid wire layer is first-party (no SDK): signing lives in `internal/infrastructure/signing/l1action.go`, wire-action structs in `internal/infrastructure/exchange/hlwire.go`; struct field order and tags are part of the signature and are pinned by recorded goldens (`hlwire_golden_test.go`) — never edit them without re-validating real orders
- signed exchange actions must be typed structs; the pipeline rejects `map[string]interface{}` actions (random msgpack field order makes their signatures nondeterministic)
- both venues execute through one pipeline: build wire action → `SignL1Action` → `postSignedExchangeAction`
- all signing handlers use the cached backend key
- the browser sends a raw key only to establish the backend session, then immediately overwrites canonical/legacy browser state with the `__AUTO__` marker and deletes `window.privateKey`; subsequent actions never retain or resend key material
- wallet initialization is checked before xyz/HIP-3 trading
- HIP-3 routing belongs in the exchange adapter
- underlying-market trading-session/close-time logic is owned by `internal/services/market_hours.go` (exact full-ID registry, ordered cash windows, maintenance futures, split-session futures, and continuous-week FX + IANA-tz `LastClose`/`IsOpen`); the 24/7 mispricing service (`internal/services/mispricing.go`) and its startup pre-warm consume it (see *Stock Mispricing*)
- bot runtime is backend-owned and should survive browser reconnects
- `PEZ_BOT_STATE_FILE` enables bot-session restore after process restart
- the desktop listener binds `127.0.0.1` by default; `PEZ_BIND_ADDR` is the explicit LAN/public opt-in and a non-loopback value requires `PEZ_API_TOKEN` at startup
- fund-moving / key / proxy / bot-control route policy is keyed by **method + route** and shared by `RequireAPIToken` and audit logging (so a protected POST cannot accidentally protect or audit a GET sibling); CORS is not an auth boundary
- every WebSocket endpoint validates handshake origin against `PEZ_ALLOWED_ORIGINS`, requires the configured API token, and keeps token material out of URLs; the trading lane additionally requires and validates an exact account scope
- Why the warm-up layer exists at all (vs. pure lazy loading + cache) is argued in full in `docs/CANDLE_WARMUP_RATIONALE.md`, including the zero-code A/B recipe (`PEZ_CANDLE_PRELOAD=0` + `/metrics`) to re-test the trade-off empirically.
- `internal/infrastructure/candlecache` owns the server-side candle store. Before readiness admission, `SelectCoins`/`FetchLiquidity` build the bounded pinned-plus-liquid startup universe and `EnsureChartUniverse` verifies the default chart dependency graph described above; liveness remains available through that barrier. After admission, one **warm coordinator** (`internal/services/warmcoordinator`, wired in `cmd/server/main.go`) owns ongoing anticipatory warming. It unions the **clickable** ticker lists the UI actually shows — `pinnedCandleCoins` ∪ top movers (`GetRankedMovers`) ∪ market-mispricing candidates (`MispricingCandidateCoins`) ∪ the watchlist hints posted by primary tabs (see *`/api/preload-hint`*) — and fills them in two passes. Display pass first (`NeedsDisplayWarm` / `WarmDisplay`): **Tier 0** the active chart, **Tier 1** interactive timeframes (watchlist before movers), **Tier 2** MISPRICE references, **Tier 3** `1w`/`1M`. Deepen pass last (`NeedsWarm` / `WarmOnDemand`) extends already-clickable series toward exchange retention so a 416d BTC `2h` fetch cannot starve AVAX `15m`. Restored history-ready series serve live chart requests from memory; the tail heals in the background. Reconcile is every ~60s. `PEZ_CANDLE_PRELOAD=0` disables the background candle store and therefore close-reference resolution; the visible chart passthrough path remains available.
- Startup readiness treats the visible `4h` chart as the same 190-day indicator-stable display dependency as `1h`/`2h`/`8h`/`1d`/`15m`/`30m` (`chartrequirements.IndicatorStableLookbackMs`; `15m`/`30m` then clamp to Hyperliquid's 5000-bar cap). The browser (`web/src/chart/chart-history-requirements.js`) requests that same reachable window on first paint so default CVD-oscillator / monthly-profile levels are computed from a complete warmup and do not rewrite when older bars prepend. After snapshot restore, `PromoteExtendedLookbacks` raises registered lookbacks toward exchange retention (`2h`/`1h`/`15m` to the ~5000-candle Hyperliquid cap, `4h` to the 600-day RVWAP source, `8h`/`1d` to 730d/1000d) and never below already-resident candle span, so hourly prune cannot throw away extra history and the warm coordinator fills the deeper window on the shared budget after `/readyz`. Live-edge promotion still retains one source interval of overlap so an exact 600-day request remains covered even though its asynchronous warm starts later. Primary-tab preload hints drive a sequential active-first plus exact accepted-watchlist browser hydration queue (maximum 50 watchlist coins); each `202` starts server-owned work and yields immediately to the next coin. Completed per-coin sources are cached for active + accepted watchlist, staged live 4h rows win over late snapshots, and active sources revalidate in the background without blanking existing lines/bands.
- The warm-up is paced by a self-managed weight budget (`PEZ_CANDLE_PRELOAD_WEIGHT_PER_MIN`, default 800/min), a single lane shared by the coordinator, backfill, and on-demand warms — **interactive chart loads never pace on it** (they `charge` it non-blocking; the coordinator `wait`s on it). It is a **token bucket** (continuous refill at the per-minute rate, burst capped to ~10s of allowance), not a fixed window, so warming can't dump a full minute's allowance in one startup burst. Because interactive cold passthroughs do *not* wait on this budget, a user flipping through still-cold tickers **during the initial warm pass can briefly collide with the coordinator and get HL 429s** — this is tolerated and self-heals (see below); raising the budget warms faster but widens that window, lowering it leaves more interactive headroom. Permanent upstream candle subscriptions keep warmed tails fresh at zero REST weight.
- The weight budget only paces the *average* rate — it does not cap how many background fetches are in flight at once. `WarmOnDemand` single-flights per `(coin, interval)` but **not** across different series, so flipping through several distinct cold tickers within a few seconds during the warm window used to spin up that many concurrent background fetch goroutines, each racing the shared budget; combined with the interactive passthroughs they collided with, that could be enough simultaneous real HTTP calls to trip Hyperliquid's actual per-IP limit far more than the "occasional 429" the design tolerates — surfacing as the clicked chart itself repeatedly 429ing instead of the one-off collision described above. `Store.fetchSem` (a size-1 channel in `store.go`) now serializes the actual upstream HTTP call across **every** background path (preload, on-demand warm, backfill), so at most one background fetch is ever in flight; interactive passthrough in `proxyHL` never touches `fetchSem` and stays exactly as fast as before.
- **Invariant: the chart currently being viewed always bypasses the warm-up queue.** `proxyHL` serves a covered range straight from memory (`X-PEZ-Candle-Store: 1`); a request the store declines (cold, off-list, degraded, or gapped) falls through to the fast Hyperliquid passthrough so the chart the user clicked paints immediately regardless of the store's warm state, and the passthrough response folds back into the store via `MergePassthrough`. It then fires `go WarmOnDemand(coin, interval)` (`warmSeriesFromBody`) — a background, single-flighted (per `coin·interval`) fill of the full lookback on the shared budget lane that registers off-list coins and their declared CVD sources. The first price frame can therefore precede full chunked depth and exact anchored-CVD enrichment on a never-warmed market; the frontend extends history and retries missing `cvdDelta` automatically while the active series receives coordinator priority. Once covered, later views serve from memory (~2 ms). The body-keyed proxy cache cannot help candles because the frontend stamps every request with `endTime: Date.now()`. Frontend-side, `prefetchAdjacentTimeframes` (`market-service.js`) warms the ±1 neighbouring timeframes on idle after a coin/timeframe switch so flips land on cached candles. This invariant is the thing to re-verify first if "chart not available" reports come back — see *Live validation* Coin And Timeframe Churn, and the `fetchSem` note below for the concurrency pitfall that can undermine it even though the passthrough path itself never changes.
- **429 / timeout self-healing**: interactive candle requests that encounter an upstream throttle or hard timeout still schedule budget-paced warming, while blank active charts retry after the cooldown (1s/2s/5s/10s). `candlePassthroughSem` bounds interactive passthrough concurrency; candleSnapshot passthroughs use `Timeout: 0` plus a **25s** RTT bound after limiter wait (probes 10s) so thin builder-dex cold loads are not killed by wait time. A truncated upstream body is `passthrough_error`, not a 200. Live 429s penalize the shared token budget. The browser retries `/api/chart-candles` on the same transient ladder as `/api/hl` and silences intentional switch cancels. `/metrics` exposes `pez_upstream_rate_limited_total`, `pez_candle_serve_total`, and `pez_candle_budget_wait_seconds`. The retired Radar regime sweep and its separate `/api/radar-candle` lane no longer consume candle capacity; Market News performs no candle requests.
- **Disk persistence across restarts** (`internal/infrastructure/candlecache/persist.go`): the store snapshots itself to `data/candle-snapshot.json.gz` (gzipped concatenated-JSON, one series per value so save/load stream without a full-store buffer or long lock holds) every 30 minutes by default and once more on graceful shutdown, and restores on boot — so a relaunch resumes warm instead of re-fetching the display window × every warmed coin. `PEZ_CANDLE_SNAPSHOT_INTERVAL` overrides the crash-checkpoint cadence when set to a duration of at least 5 minutes; the longer default avoids repeatedly rewriting a large store when graceful shutdown already writes the freshest tail. Current rows persist whether gap state is known, the unverified-gap origin, and the REST-verified-through instant. Legacy rows without that state are restored conservatively and scanned for their first timestamp discontinuity; current verified sparse rows retain their proven range instead of having no-trade buckets reclassified as gaps. The startup barrier repairs any selected series still cold, degraded, gapped, or shallow before readiness opens. `LoadSnapshot` fires `onRegister` per restored series so cache-owned WS subscriptions are recreated subject to the 64-feed cap; it never clobbers live data, ignores snapshots older than 7 days or from another format version, and a truncated file loads whatever valid prefix remains. Saves are atomic (tmp + rename), single-flighted, and copy candle rows under the series read lock so gzip cannot race `ApplyWSCandle`. Each series persists its `lastNeededMs` idle clock, and both sides enforce the idle TTL: `SaveSnapshot` drops series already idle past `seriesIdleTTL` (5m/30m CVD sources inherit the coin's freshest stamp, matching eviction), while `LoadSnapshot` skips idle rows before registration unless `PrepareStartupUniverse` already pinned them. Both paths sweep orphaned `*.tmp-*` files older than 1h. `PEZ_CANDLE_SNAPSHOT=0` disables snapshots; `PEZ_CANDLE_SNAPSHOT_FILE` overrides the path; `data/` is gitignored.
- the store declines to serve while degraded (market WS down) or while a series has an unverified candle gap — requests fall back to passthrough, and the passthrough response itself repairs the store; coverage only extends from requests that reach the present or adjoin existing coverage, never from pure historical scrollback on a cold series. Empty REST never pins `coverageStartMs`. `EnsureChartUniverse` skips a failed market instead of `log.Fatalf` after the listener is up.
- **the series set is bounded by idle eviction** (July 2026; previously "never evicted" was an accepted trade): `pruneOnce` trims candle depth within a series to lookback + 7d slack, and the same hourly pass (`evictIdleSeries`) removes whole series nothing has **needed** for `seriesIdleTTL` (7d) — deleting the data, firing `SetOnEvict` → `wsManager.RemovePermanentCandleSubscriptions` (drains ALL permanent refs for the key; client-held refs and their upstream feed are untouched), and dropping the series from future snapshots. "Needed" = served to a chart (`ServeInfoRequest`, even while degraded), warmed (`WarmOnDemand`/`MergePassthrough`), or touched by the warm coordinator's 60s reconcile (`Deps.Touch` → `Store.MarkNeeded` for every union member, warm or cold) — so pinned/movers/mispricing/watchlist coins never age out while listed. Live WS ticks deliberately do NOT count as "needed" (the subscription would keep the series alive and the series would keep the subscription — nothing would ever age out). The 5m/30m CVD source series inherit their coin's freshest clock (coin-level max propagated into their own stamp), so `ComputeCvdDeltas` keeps its sources while any chart of the coin is in use. An evicted coin re-registers transparently on the next click via the normal passthrough → `MergePassthrough` → `WarmOnDemand` path — worst case is one extra passthrough after 7 idle days
- WS-down degradation and gap state are separate per-series flags and must stay separate: `degraded` clears on the first post-reconnect tick (safe — the cumulative bucket replace covers an outage contained in that bucket, and a crossed boundary surfaces as a jump), but an unverified gap (`unverifiedGapFromMs`) clears ONLY when a backfill or a covering passthrough actually fetched the range (guarded by a gap generation counter against jumps landing while a fetch is in flight). Ticks clearing gap state was the post-sleep hole bug: the store served the sleep window as missing-candle "data" while the backfill sat behind the weight budget. Gap backfills retry on ticks every cooldown, so an enqueue dropped on a full queue (all series gap at once after a wake) cannot orphan the gap. **`1M` adjacency is calendar-month** (`nextOpenMs`), not +30d, so Jan→Feb is contiguous. Browser reconnect recovery uses the same calendar (`currentBucketOpenSeconds`: UTC month start for `1M`, Monday 00:00 UTC for `1w`) so a current-month/current-week tail is not treated as stale after an HL expire. `ServeInfoRequest` copies the slice under the same read lock that observed `unverifiedGapFromMs == 0`, so a concurrent WS jump cannot be published as complete history.

### In-Memory Decision Cache, Token Optimization & Circuit Breaker
- Upstream Jev HTTP calls are cached and deduplicated via a thread-safe in-memory cache keyed by SHA-256 state hashes.
- For identical market states within a 2.5s window (e.g., repeated orderbook queries during rapid tick events), cached decisions are returned in <1ms, avoiding token waste and latency.
- **3-Strike Circuit Breaker:** Consecutive failure tracking trips into a 20s cooldown upon 3 consecutive upstream HTTP 5xx errors or network timeouts, returning 0ms fail-fast errors to prevent thread starvation or socket leaks.

### Bot Orderflow Strategy Integration
- Strategy `jev-orderflow` inside `BotService` dynamically adjusts quote skews based on Jev OFI conviction.
- **Avellaneda-Stoikov Inventory Dampening:** Adjusts quoting skews relative to real-time account position in the traded instrument, tightening offloading quotes and backing away accumulating quotes when inventory ratio exceeds $\pm 25\%$.
- **Circuit Breaker & Hysteresis:** Automatically cancels quotes and enforces a 30s hysteresis cooldown window (`toxicHaltUntil`) when adverse selection risk exceeds 0.65 (`toxicFlowRisk > 0.65`), preventing toxic fills and quote-churn during aggressive market sweeps.

### TypeSafe Jev Engineering Blueprint Subsystems
The backend infrastructure package (`internal/infrastructure/typesafe/harness.go`) and standalone Python suite (`scripts/jev_validation/jev_harness.py`) implement the full 9-subsystem architecture synthesized from Diogo Almeida's TypeSafe design notes:
- **Addressable Chunk Store & Visibility Ladder:** Typed state chunks (`tool_call`, `tool_output`, `reasoning`, `user_turn`, `file_diff`, `instruction`, `market_state`) scored dynamically per query into 4 visibility tiers (`hide`, `short`, `long`, `full`), eliminating query-blind compaction.
- **FilterHeatmap:** Filters 2,400+ line outputs (grep, verbose logs, orderbook depth) down to highest-scoring lines within token budgets.
- **KV Cache Reuse Evaluator:** Returns a typed `noul` decision with probability on whether to reuse cached prefix or rebuild context.
- **Priced Routing Cost Engine:** Implements the exact routing trap arithmetic ($25Y + 5Z$ vs $3X + 20Y + 8Z$ vs purpose-built context $3X' + 15Y + 3Z + 5Y_{\text{summary}}$) to price routing per context rebuild rather than per token.
- **Tiered Tool Disclosure:** 3 disclosure tiers (Tier 1 snippets, Tier 2 schemas on demand, Tier 3 docs) with plain-text intent routing via `RouteTool`.
- **Programmable Permissions with Deep Script Inspection:** Declarative execution policies (`deny` if touches `~/.ssh` or `.env*`, `deny` on network egress without deploy scope, `ask` outside repo root, `allow` read-only/tests). Integrated directly into `AuditPreTrade`.
- **Sub-Agent Concurrency & Goal Deduplication:** Separates read tasks from write tasks (`ExecuteReadOnly` executes concurrently with zero lock contention), while `SubgoalRegistry` coalesces in-flight and completed tasks.
- **Conditional Instructions & Security Routing:** Dynamic matching of condition-bound instructions (`touches *.tsx`, `inside billing/`) immune to compaction, and file sensitivity classification (`open`, `standard`, `restricted`, `custom`) for model provider governance.
- **Shared Retrieval Cache:** `SharedRetrievalCache` caches expensive L2 depth, OFI, ATR, and volume profile calculations, shared across all read-only background evaluators.
